# SDD 핵심 규칙

목표: AI와 작업하며 사라지기 쉬운 의도, 결정의 맥락, 시행착오를 코드 옆에 남겨 다음 작업자가 이어받을 수 있게 한다.

## 문서
- 개발 단위마다 `specs/YYYY-MM-DD-작업명/`에 `plan.md`(무엇을)와 `decisions.md`(왜)를 둔다. 작성 방법은 자유다. 어떤 도구로 설계하든 별도의 설계 문서 대신 처음부터 이 두 문서에 쓰고, 도구가 만드는 작업 분해 문서는 같은 폴더의 `tasks.md`에 둔다.
- 코드를 바꾸기 전에 관련 스펙을 읽는다. 진행 상황과 검증 결과는 AI가 갱신하고, 의도·범위·목표·완료 기준·검증 방법은 사람의 선택을 받아 바꾼다.
- 구현과 스펙이 어긋나면 코드와 스펙 중 무엇을 고칠지 사람에게 묻고, 정해진 대로 같은 변경에서 맞춘다.
- 범위 밖 작업은 구현하지 않고 `plan.md`의 "나중에 할 일"에 적는다.

## 결정의 라벨
- 번호는 스펙 폴더마다 D1부터 이어지며 재사용하거나 다시 매기지 않는다. 다른 스펙의 결정은 `2026-11-24-작업명#D2`로 참조한다.
- 출처: 선택된 안을 처음 낸 쪽과 선택한 쪽을 나타낸다. 추천은 제안으로 보지 않는다. 예를 들어 사람이 "표나 JSON 중에"라고 했다면 표와 JSON은 모두 사람의 제안이다.
  - `user-suggested`: 사람이 제안하고 사람이 선택
  - `ai-suggested`: AI가 제안하고 사람이 선택 (AI가 낸 옵션의 승인 포함)
  - `ai-selected`: AI가 제안하고 AI가 선택
  - `미정`: 아직 선택되지 않았거나(상태 `선택 대기`), 선택됐지만 누가 했는지 확인되지 않음(상태 `유효`). 확인되면 위 라벨로 바꾼다.
- 영향도
  - `foundation`: 프레임워크 선택, 핵심 코어 등 스펙의 근간
  - `significant`: 여러 부분에 영향
  - `local`: 단일 단위에 영향
  - 프로젝트 밖(홈 디렉터리, 시스템 설정, 외부 서비스 등)에 영향을 주면 `local`이 아니다. 애매하면 더 높은 쪽으로 분류한다.
- `local`은 나중에 이유가 궁금하거나 다시 검토할 만한 것만 기록한다. 코드로 알 수 있거나 부담 없이 바꿀 수 있는 선택은 기록하지 않는다. 사람이 기록을 요청하면 기록한다.
- 실제로 나온 옵션과 근거만 적는다. 다른 안을 논의하지 않았으면 옵션에 "다른 안은 논의하지 않음"이라고 적고, 확인되지 않는 근거는 묻거나 "확인되지 않음"으로 남긴다.

## 선택
- 옵션에 사람의 제안이 하나라도 있으면 영향도와 무관하게 사람이 선택한다. "A나 B 중 알아서"처럼 맡기더라도 추천과 이유를 제시하고 선택을 받는다. 선택 전까지 `선택 대기`로 기록하고 그 결정에 의존하는 구현을 미룬다.
- 옵션이 모두 AI의 제안이면 `local`은 AI가 선택하고, 기록한 것은 `ai-selected`로 두어 마칠 때 모아 보고한다. `foundation`과 `significant`는 사람에게 묻는다. 물을 수 없는 환경에서 진행했다면 `ai-selected`로 기록하고 우선 검토 대상으로 보고한다.

## 변경
- 기록한 결정은 지우지 않는다. 기존 결정에서는 상태, `선택 대기`의 선택·출처·근거, `미정` 출처를 채우고, 근거 아래에 시행착오나 재논의 이유를 날짜와 함께 덧붙일 수 있다. `Superseded` 결정은 그대로 둔다.
- 번복할 때는 새 결정에 이유를 적고, 기존 결정의 상태를 `Superseded by D5`(다른 스펙이면 `Superseded by 2026-11-24-작업명#D5`)로 바꿔 작업자에게 보고한다.
- 사람이 선택했거나 출처가 `미정`인 결정은 사람만 번복한다. `ai-selected`인 `local` 결정은 사람의 새 제안이 없으면 AI가 번복하고 보고할 수 있다.
- 다시 논의할 결정은 상태를 `유효 (재논의)`로 바꾼다.
- 관련 결정이 없는 시행착오는 `decisions.md` 끝의 `## 시행착오`에 적는다. 이 절은 새 결정이 추가되어도 끝에 둔다.
